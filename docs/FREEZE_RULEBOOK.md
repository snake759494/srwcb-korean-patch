# 프리징 규칙표

증상마다 따로 막던 방식을 그만두기 위해 만든 문서다. 릴리스 노트 61개, 프로젝트 기억
37개, 깃허브 이슈 전문, 감사 코드 27개에서 **해결 사례 236건**을 채굴하고, 같은 불변식을
어긴 것끼리 묶어 규칙으로 만들었다.

---

## 왜 규칙이 필요했나

v0.11.45 에서 **v0.11.40 에 고쳤던 EX 23화가 다시 깨진 채 여덟 판이 배포**됐다.
게이트는 있었다. 그런데 그 게이트가 수정기와 **같은 함수**를 다시 부르는 방식이라,
수정기가 건너뛴 자리는 게이트도 보지 못했다. "이벤트 포인터 잔류 0" 이라고 보고하면서.

이게 이 프로젝트에서 게이트가 실패한 전형이다. 그래서 규칙과 함께 **게이트 설계 원칙**을
못 박는다.

## 게이트 설계 원칙

1. **수정기를 다시 부르지 마라.** 게이트는 레트일 원본과 최종 이미지를 직접 대조한다.
   수정기의 필터·상수·휴리스틱을 공유하면 수정기의 사각지대를 그대로 물려받는다.
2. **판별력을 증명해라.** "게이트가 있다" 로는 부족하다. 배포본에 그 게이트가 막아야 할
   **과거 결함을 되심었을 때 실패하는지** 확인해야 한다. → `audit/verify_gate_power.py`
3. **탐지기 자체를 검산해라.** 검사 대상 개수를 레트일에서 세어 기대값과 맞춰 본다.
   대상이 0개인데 "위반 0" 으로 통과하는 것이 가장 위험하다.
4. **조용한 건너뛰기를 만들지 마라.** 짝지을 수 없는 경우는 `continue` 가 아니라 실패다.
5. **우리 파서의 레코드 분할에 의존하지 마라.** 변위가 0xFF 를 품으면 레코드 훑기가
   레트일과 다른 데서 끊긴다. 서수·길이는 그때 못 믿는다. 실패 양상에서 직접 나오는
   불변식을 써라.

## 규칙

### R-LAND · 이벤트 참조는 레코드 시작에 착지한다
`audit/verify_pool_event_refs.py` — **enforced**

> 레트일에서 레코드 시작을 겨누던 대사 포인터는, 배포본에서도 **어떤 레코드의 시작**에
> 착지해야 한다.

번역으로 레코드가 밀렸는데 변위를 안 고치면 스크립트가 남의 레코드 한가운데로 뛴다.
덮는 사례: 제2차 브리핑 정지(v0.10.7, 21개 시나리오) · 전투 후 정지(#39) ·
EX 23화 듀라크실(#28, v0.11.40 → v0.11.45 회귀).

**서수로 판정하지 않는다.** 분할이 흔들리면 서수가 밀린다. 착지 지점만 본다.
host 매핑은 레코드 길이가 아니라 **레코드 시작부터 참조 자리까지의 바이트 일치**로 한다
(길이로 거르면 제2차 sc4 처럼 잡아야 할 자리가 통째로 빠진다).

### R-OBJHDR · 작전목적 머리글의 L 은 패배조건 위치를 가리킨다
`audit/verify_record_prefix.py` — **enforced (2026-09-28 정정)**

> `E9 03 FE FF 04 00 <L> 00` 머리글은 개수·위치가 레트일과 같고, **L = 패배조건 시작 − 2 − blk** 다.

★ **예전 불변식("L 이 레트일과 바이트까지 같다")은 틀렸다.** `<L>` 을 창폭으로 읽었지만
`E7 02` 핸들러(제2차 0x800C1700)를 역분석해 보니 `blk + L + 2` 에서 패배조건을 읽는
**오프셋**이다. 번역으로 승리조건 길이가 바뀌면 L 도 바뀌어야 한다. 옛 게이트는 L 을 레트일
값에 묶어 둬서 제2차 14곳의 틀린 L 을 통과시켰다(아래 R-OBJWIN).

찌그러지면(`04 XX`) 목표가 바뀌는 순간 멈춘다: EX 마사키 9·11·27화, 류네 45·49화,
슈우 58화(#10·#11·#24, v0.11.33) — 개수 검사로 계속 잡힌다. 192개(51/70/71)를 대조한다.

### R-OBJWIN · 작전목적 창(E7 02)은 제 블록을 가리키고 블록 L 은 실제 길이다
`audit/verify_objective_windows.py` — **enforced (신규, 2026-09-28)**

> 레트일 `E7 02` 가 블록 k 를 겨누면 배포본도 블록 k 의 시작을 겨눈다. 모든 블록의 L 은
> 패배조건 시작 − 2 − blk 이다.

블록: `04 00 L 00 | 승리 FF [FF] | 패배 FF [FF]`. `E7 02` 는 두 문자열을 **스택 128바이트
버퍼(sp+16)에 0xFF 까지 무검사 복사**한다. 변위가 스테일이면 쓰레기 u16 을 오프셋으로 읽어
시나리오 밖(음악 데이터)을 수 KB 복사하고 메인 루프의 저장된 ra 를 덮는다 → **장면이 끝나
메인 루프가 반환하는 순간** BIOS 예외(EPC 0x47003544). 제2차 8화 "브라이트 대사 뒤 멈춤"
(#1, 옛 저장소 #32 는 풀 참조로 잘못 진단). 제2차 53 · 제3차 79 · EX 78 사이트 대조.

**블록은 모양으로 찾지 않는다.** `FF 04 00 ?? 00` 모양은 스크립트 속에도 있고(EX sc1
`F1 FF 04 00 11 00 …`, 고치면 스크립트가 깨진다), 진짜 블록인데 앞이 FF 가 아닌 것도 있다.
블록 = 레트일 `E7 02` 목표 ∪ 머리글 뒤 블록. 배포본 대응은 ① 레코드 시작 → 레코드 서수
② 머리글 뒤 → 머리글 서수 ③ 그 밖 → 레코드 안 오프셋. ②를 레코드 오프셋으로 풀면
0xFF 피연산자 보정으로 레코드 시작이 달라진 시나리오(제2차 sc4, EX sc8·sc23)에서 틀린다.
수정기: `tools/objective_windows.py` (image-build step_sce 마지막).

### R-COLUMN · 스페이서 칸은 레트일과 같은 자리에서 나뉜다
`audit/verify_ex_chapter_menu.py` — **enforced (신규, 2026-09-28)**

> EX·트레이닝 장 선택(UI 94~97)의 스페이서 줄마다 이름 칸 폭·끝 phase, 둘째 칸 첫
> 글자 위치가 레트일과 같다(원문은 모든 줄이 8).

`fit_span` 은 줄 **전체** 폭만 원문 이하로 맞춘다. 넘치면 공백을 깎는데, 그러면 칸 경계가
어긋나 구분선이 글자에 걸린다. `" 레벨 어려움"` 은 18 로 원문 17 을 넘어 공백이 깎였다
(#4, 옛 저장소 #30 의 수정이 이것을 낳았다). 트레이닝 모드도 같은 상태였다.

### R-TBLCOPY · 실행파일 안 표 사본은 실물과 같다
`audit/verify_bmess_tables.py` — **enforced (신규)**

> 레트일 실행파일이 어떤 BMESS 목차표 사본을 갖고 있었다면, 배포본의 같은 자리에는
> **배포본 아카이브의 표**가 있어야 하고 레트일 표는 어디에도 남지 않는다.

표가 스테일이면 전투 대사를 블록 한가운데부터 읽어 전투가 멈춘다(트레이닝 모드 실측,
v0.11.37). 네 실행파일이 세 게임의 표를 모두 품으므로 죽은 사본도 남기지 않는다. 15건.

### R-PAGE127 · 대사 한 페이지는 127바이트를 넘지 않는다
`audit/verify_page_bytes.py` — **enforced**

> 페이지 기록량 + 종단자 ≤ 128. 페이지 경계는 3번째 `F6`/`F7`/`FF`.

넘으면 호출자 스택의 128바이트 줄버퍼를 넘어 저장된 `s0`·`s1`(디스패치 표 주소)을 덮고,
`jr 0xFFFFFFFF` → BIOS 미해결예외 루프 → RAM 정지(v0.11.40, EX 23화).

### R-BYTES · 스크립트 바이트는 피연산자 말고 안 바뀐다
`audit/verify_sce_script.py` — **partial** (풀 **앞** 구간만 본다)

> 시나리오 스크립트 구간에서 레트일과 달라질 수 있는 바이트는 대사 포인터의 2바이트
> 피연산자뿐이다.

덮는 사례: `F0 00 <변위>` 를 옵코드로 오인해 다음 명령을 덮어쓴 것(v0.11.39, EX 6곳·
제3차 2곳). **한계**: 풀 **안** 이벤트 스크립트 레코드는 검사 범위 밖이다(파일의 29~47%).

### R-LANDGLYPH · 표 엔트리는 글리프 경계에 착지한다
`audit/verify_ui_runs.py` — **enforced**

> UI 문자열표가 레코드 **안쪽**을 겨눌 때, 착지 바이트는 글리프 경계여야 한다.

어기면 착지 바이트가 VM 옵코드(≥0xF6)로 오독돼 멈춘다(v0.11.34 유닛 개조).

### R-F8LOOP · 치환 패딩 루프에 하한 검사가 있다
`audit/verify_vm_hardening.py` — **enforced**

> 배포본에 하한 검사 없는 치환 패딩 루프가 0곳, 같은 지문이 레트일에는 2곳.

치환값이 정적 폭보다 길면 부호 없는 32비트 카운터가 2³² 번 돌며 RAM 을 민다(v0.11.37).

## 메타 게이트 — 판별력 증명

`audit/verify_gate_power.py` 는 배포본에 **과거 결함을 되심고** 게이트를 돌린다.

    정상 배포본 -> 위반 0건       (거짓 경보 없음)
    결함 주입본 -> 위반 1건 이상  (판별력 있음)

| 표본 | 되심는 결함 | 결과 |
|---|---|---|
| F-pool-ref | 이벤트 참조를 레트일 변위로 (v0.11.45~52) | 9곳 → 9건 |
| F-f0-clobber | `F0 00` 변위 뒤 명령 훼손 (v0.11.39) | 6곳 → 6건 |
| F-page-128 | 대사 페이지 128바이트 초과 (v0.11.40) | 1곳 → 1건 |
| F-midglyph | 문자열표를 글리프 한가운데로 (v0.11.34) | 4곳 → 4건 |
| F-objhdr | 작전목적 머리글 뭉갬 (v0.11.33) | 9곳 → 3건 |
| F-bmess-tbl | BMESS 목차표를 레트일 표로 (v0.11.37) | 2곳 → 4건 |
| F-objwin-disp | E7 02 변위를 블록 앞으로 어긋냄 (v0.11.54, #1) | 6곳 → 6건 |
| F-objwin-len | 작전목적 블록 L 을 실제와 다르게 (v0.11.54) | 9곳 → 9건 |
| F-objhdr-len | 머리글 L 을 실제와 다르게 — 옛 게이트는 못 잡았다 | 9곳 → 7건 |
